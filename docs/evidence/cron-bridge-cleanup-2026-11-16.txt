# Cron bridge double-ownership cleanup — moses (2026-11-16)

## Symptom
The doctor's `Cron bridge ownership` check flagged 54 crons as DOUBLE-OWNED: a
fleet-bridge systemd timer AND a stale Hermes jobs.json row left after the job
migrated to the timer (double-fire, Errno 17). Each such FAIL blocked pushes.

## Fix
For each of the 54 doubles, `hermes cron remove <id>` — drops ONLY the stale
Hermes scheduler row; the systemd timer (the real owner) keeps running the cron
(verified active after each removal). Non-destructive by design. Durability: the
installer (`install-crons.sh`) skips a bridged cron when its timer is ENABLED
(present in timers.target.wants/) — both of the half-migrated timers below were
enabled as part of this fix, so a fleet-update reinstall does NOT re-create the
removed rows — the 2 half-migrated timers were enabled here, and the other 52
were verified ACTIVE (systemd active implies enabled), so the installer skips
all of them.

Two of the 54 (`fleet-bus-failover-watchdog`, `orch-weekly-cost-report`) had a
GENERATED-BUT-NOT-ENABLED bridge timer — the Hermes row was their live owner.
After removing the stale row their bridge timers were enabled
(`systemctl --user enable --now`) to complete the migration rather than orphan
the cron; both verified active + enabled.

## Durability re-visit (2026-11-16 21:15) — the removal was NOT durable at first
A row-removal alone did NOT persist: the very next `fleet-update.sh` re-created
52 of the removed rows, so the doctor flipped back to 52 FAIL.

ROOT CAUSE (verified): the 63 bridge timers exist as `fleet-bridge-<name>.timer`,
but the `~/.config/systemd/user/timers.target.wants/fleet-bridge-<name>.timer`
enable symlinks still pointed at the PRE-RENAME `cortex-bridge-<name>.timer`
target (leftover from the 2026-11-03 STEADFASTE-FLEET rename) — 59/63 were
DANGLING. `systemctl` still reported them `enabled` (the link exists), but
install-crons.sh's durable bridge-guard uses `test -e` which FOLLOWS the link ->
dangling = FALSE -> the installer did NOT skip the bridged cron and re-created
its Hermes row. Only the 4 with a non-dangling link (incl. the 2 enabled here)
stayed clean.

DURABLE REPAIR (applied, non-destructive, no repo change): re-point each want
symlink at the live unit —
`systemctl --user reenable fleet-bridge-<name>.timer` (59 links fixed, 0 left
dangling; does not start/stop any unit). Now `install-crons.sh --dry-run`
reports `✓ Skipping '<name>' — owned by the fleet cron bridge` for all 63 no
longer involves re-adding rows, and the doctor is again 0 FAIL
(`ℹ️ every one of 63 bridged names has exactly one owner`).

LESSON (fleet-wide): a `hermes cron remove` cleanup is durable ONLY when the
bridge timer's want-symlink RESOLVES (target on disk). After the fleet rename,
stale `cortex-bridge-*` want links defeat every `test -e` bridge-guard. Any
agent whose doctor re-flags doubled crons after a fleet-update should first run
the `systemctl --user reenable fleet-bridge-<name>.timer` repair (or
`systemctl --user daemon-reload && reenable --all` equivalent) and re-verify
with `install-crons.sh --dry-run` before re-removing rows.
