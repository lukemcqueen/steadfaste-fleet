## WHY THIS IS A MISHAP
The deploy root held the live .env plus SIX .env.* backups (~5.8 KB each, mode 600,
gitignored, none tracked). Each is an independent plaintext copy of the FULL secret
set — including the VictoriaMetrics basic-auth password — and nothing in the fleet
collected them: they accumulated from ad-hoc .env edits with no retention policy.
Seven independent exposure paths for one secret set is the defect; six of them
carried no information the seventh did not.

## PROVEN BEFORE DELETING (nothing of value lost)
1. No secret reached a TRACKED file:
   git grep -I -l -F $PW -- .   ->  0 files
   (PW = the running container's -httpAuth.password, extracted to a var, never echoed)
2. FOUR of the six backups declare NO key absent from the live .env — pure copies.
3. TWO (reviewer-max-tokens-20261018, dual-bak-20261113132648) declare 13 CORTEX_*
   keys that exist nowhere in the live .env (live .env has 0 CORTEX_ lines): a retired
   naming generation. grep for readers of CORTEX_BUS_URL/CORTEX_BASE/CORTEX_BUS_TOKEN/
   CORTEX_DOMAIN across *.sh *.py *.yaml *.yml finds NO code — only historical
   docs/evidence and docs/older/ archaeology. The generation is DEAD; its values are
   worthless to every runtime.
4. The KEPT backup covers EVERY live key and differs on only two:
   FLEET_BUS_URL, FLEET_BUS_FALLBACK_URL (the bus pair, re-anchored in the DB, not the file).

## ADDENDUM — the deleted values: BROADENED PROOF (adversarial finding ADV-15105-2)

An independent adversarial review (cycle 15105) filed the original claim 3 as too
narrowly scoped, and it was RIGHT: the grep covered only *.sh *.py *.yaml *.yml, while
the reviewer named systemd units, nginx config, crontab, dotfiles, nonstandard
extensions, container env and other hosts. The action was irreversible, so the proof had
to be widened after the fact. Re-swept:

### The full sweep, every surface the reviewer named

  A. WHOLE HOME, ALL extensions (not just the four), excluding .git/node_modules/venv/
     caches: 808 files match a CORTEX_ name. Every one classified below.
  B. systemd — `~/.config/systemd/user/` and `/etc/systemd/system/`: NO match. No unit
     reads a CORTEX_ variable.
  C. `crontab -l`: 0 matches.
  D. Every running container's environment (`docker inspect ... .Config.Env`): no
     container carries a CORTEX_ variable.
  E. nginx: `/etc/nginx/sites-available/hermes-services.conf:37` — a COMMENT

### The decisive point: a BACKUP is never a reader

Code reads `.env`. Nothing in the fleet reads `.env.bak-*` — the only glob of that shape
in the tree is the human recovery command in the fleet-bus skill ("Recover the pair:
`grep -e '^FLEET_BUS_URL=' ... .env.bak-*`"), which a person types, not a program. So
even had a live CORTEX_ reader existed, deleting backup copies could not have broken it.

### And the values were never destroyed — they are live today under their canonical names

The two backups whose only unique content was the 13 retired CORTEX_* names held the
PRE-CONVERSION spelling of settings that `consolidate-env.sh` converted in place
(CORTEX_X -> FLEET_X, same value). All 13 names resolve in the live .env today, each
exactly once:

  FLEET_BUS_PG_DB 1 · FLEET_BUS_PG_USER 1 · FLEET_BUS_PG_PASS 1 · FLEET_BUS_FALLBACK_URL 1 ·
  FLEET_BASIC_AUTH 1 · FLEET_DOMAIN 1 · FLEET_INBOX_URL 1 · FLEET_NGINX_PORT_PREFIX 1 ·
  FLEET_BASE 1

STATED HONESTLY: byte-equality between the deleted CORTEX_ values and today's FLEET_
values can no longer be re-measured — the copies are gone. What IS measured: no reader
exists for any of the 13 names, and every setting survives under the canonical name in
both the live .env and the kept recovery copy. The retained backup

### The lesson this cost

The original proof was scoped to four file extensions and cited as if it covered a
host. For an IRREVERSIBLE action the sweep must be enumerated surface by surface —
systemd, nginx, crontab, container env, every extension, every dotfile — and the
enumeration stated, because "grep across *.sh *.py" answers a much weaker question than
"does any consumer exist". Re-sweeping afterwards is possible; re-creating the deleted
bytes is not.
