## 5. The blip, proven from the watchdog's OWN run history (independent of bursts)

$ journalctl --user -u fleet-bridge-fleet-bus-failover-watchdog.service   (last 400 lines = 200 ticks)
  tick-duration histogram:
    {0.0: 5, 1.0: 140, 2.0: 49, 3.0: 4, 7.0: 1, 10.0: 1}
  outliers (>3s):
    2026-11-25T13:35:00+09:00   10.0s
    2026-11-25T13:55:00+09:00    7.0s
  The tick probes TWO URLs, each with an 8 s urlopen timeout, so ~1-2 s is the
  healthy cost and a >8 s tick means a probe TIMED OUT — `endpoints_reachable()`
  then returns False and `consecutive_failures` increments. The 10.0 s tick is
  the measured origin of Luke's alert: on that tick the pre-fix orchestrator
  branch fired "Moses health check FAILED (1/4)". The next tick was healthy, so
  the state reset to `consecutive_failures=0 / last_status=idle` — the
  self-healed signature, which is why the report said "Moses is up".

  Independently corroborated by a burst against the live listener:
    25 concurrent GETs -> https://realgospelmessage.org:13007/health
      measured:  8.1s  {'TimeoutError': 25}      <- all queued past the 8 s cap
                 2.2s  {200: 25} ... (later samples all pass)
    Single probes are ~0.3 s and 200 every time. The burst is INTERMITTENT —
    every sample measured above is reported, not just the failing one — because
    it needs the fleet's probes to land in the same tick to fill the bucket.
    The bus port (:13004) answers 401 instantly, so this is the health
    listener's limits, not a network or service fault.

  Mechanism (docs/runbooks/health-throttle-false-unreachable.md): the xx007
  health block sets `limit_conn conn_limit 10` + `limit_req zone=general
  burst=10 nodelay` as the public DDoS ceiling; the FLEET is meant to bypass it
  via the allowlist below. Without that allowlist, probes arriving in a fleet
  tick exceed the bucket, queue, and trip the watchdog's own 8 s timeout.

## 6. Root cause: the live nginx is the STALE revision
file: /etc/nginx/hermes-zone-defs.conf   (mtime Aug 10 — never re-deployed)
  LIVE limit zones:
    limit_req_zone  $binary_remote_addr zone=general:10m rate=20r/s;
    limit_req_zone  $binary_remote_addr zone=auth:10m   rate=5r/s;
    limit_conn_zone $binary_remote_addr zone=conn_limit:10m;
  REPO template (ops/install/deploy/nginx/hermes-zone-defs.conf):
    limit_req_zone  $limit_bypass zone=general:10m rate=20r/s;
    limit_req_zone  $limit_bypass zone=auth:10m   rate=5r/s;
    limit_conn_zone $limit_bypass zone=conn_limit:10m;
  The live file has NO `geo $limit_bypass` and keys every zone on
  `$binary_remote_addr`, so the fleet's own probes are limited. The repo
  template re-keys them onto the allowlist (an EMPTY key => no limit).
  fleet-update's deploy_nginx_configs() cannot apply this itself — it needs
  root for /etc/nginx and only PRINTS the sudo command, which is why the stale
  state persisted. OPERATOR FIX (root required, both orchestrator hosts):
    sudo cp <HOME>/steadfaste-fleet/ops/install/deploy/nginx/hermes-zone-defs.conf \
        /etc/nginx/hermes-zone-defs.conf
    sudo nginx -t && sudo systemctl restart nginx
  RESTART, not reload: a limit-zone KEY change is refused by reload
  ([emerg] ... uses the "$limit_bypass" key while previously it used the
  "$binary_remote_addr" key), leaving the stale worker serving.
