# Skill source parity - deployed tree vs repo source

Regenerate with: `python3 ops/scripts/manage/check-skill-drift-parity.py`

Run identity: this file is written by that command when it is run by hand
from a repo checkout, so the commit carrying this file IS the record of the
run that produced the table at the bottom. `git log -1 --format=%h --
docs/evidence/skill-drift-parity.txt` names that commit, and `git diff
<that>~ -- docs/evidence/skill-drift-parity.txt` prints the previous counts
— which is what settles any move between runs: a deploy copies repo content
into the deployed tree, so files leave `skipped ... repo ahead` and enter
`in sync`; a skills backport changes them in the repo first, so the repo
runs ahead until the next deploy. Counts that move without a deploy or a
repo skills change are the signal to look at. NOTE: the fleet deploy does
NOT run this command — see "Run provenance" below for who does.

A deployed skill file whose content appears in neither the repo working
tree nor any committed revision of that path means a lesson was written on
this host and never copied back: it is stranded here, and the deploy's
drift guardrail refuses to overwrite it, so it never reaches the fleet.
Direction is decided by content, not mtime, so a fresh clone cannot hide it.
Deploy banners (the 3-line SOURCE header) are not compared.

A second class is a file the repo does not carry AT ALL while a repo-owned
skill dir owns it (an ancestor directory carries a repo SKILL.md). That is
measured by PATH: a repo SKILL.md routing to `references/foo.md` which only
the deployed tree holds is a dangling route the fleet never receives. Each
entry is marked `dropped-from-repo` (the path is in repo history, so the
file was deleted while the deployed copy stayed) or `never-committed`.
A file under no repo-owned skill dir is a Hermes default and stays skipped.

Re-verification: `python3 ops/scripts/manage/check-skill-drift-parity.py
--check` re-derives every count below from the live trees and exits
non-zero on any mismatch, so these counts are checkable rather than
asserted once. The record of the run is the check itself: re-run it to
reproduce these numbers, and diff this file against its parent revision
to read the previous counts. Callers of --check:
ops/scripts/manage/capture-crons-receipt-evidence.py,
the soul-refinement evidence script, and
ops/scripts/manage/verify-learning-system-hardening.sh (the cycle
evidence script — see "Run provenance" below). NOTE: the fleet
deploy does NOT run it — an earlier version of this paragraph claimed it
did, which was wrong.
