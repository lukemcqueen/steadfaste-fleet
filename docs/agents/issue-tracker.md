# Issue tracker: the fleet task-db (tasks schema)

Issues, tickets, stories and slices for this repo are tracked in the **fleet
task database** — the `tasks` schema on each host's `mycortex-postgres` — not in
GitHub Issues. This is a custom ("Other") tracker; the engineering skills
(`/to-tickets`, `/triage`, `/to-spec`, `/wayfinder`) read and write it through
`task-db.py` or the `task_*` MCP tools.

## Why not GitHub

`gh` is not authenticated on this host (git-over-HTTPS push works, but the `gh`
CLI does not), and the fleet already has a durable, postgres-backed task system
with statuses, RLS isolation, and Telegram visibility. Re-using it avoids a
second, divergent store.

## Conventions

- **CLI**: `~/.steadfaste-fleet/scripts/task-db.py` (deployed); resolved repo via
  `--repo`, else the session repo, else the git repo at the working directory.
- **MCP**: `task-add`, `task-list`, `task-pending`, `task-update`,
  `task-claim`, `task-report`, `task-verify`, `task-board` (server `task-mcp.py`).
  Queries are repo-scoped and strict by default; `--repo ALL` is the explicit
  fleet view.
- **Create a ticket**: `task-db.py add "<title>" --priority <n> --project
  steadfaste-fleet --repo steadfaste-fleet --scope fleet --source manual`.
  Add the standard triage labels (see `docs/agents/triage-labels.md`) as JSON
  `tags`.
- **List open tickets**: `task-db.py list --status pending`
  (or `--claimable` for the worker pool, `--board` for the board).
- **Blocking edges**: prerequisite slices are declared via the story/slice
  hierarchy (`add --kind story`, then `add --kind slice --parent <story-uuid>`).
  A worker must check its slice's prerequisites are `pending` before claiming;
  a slice blocked by an unmet prerequisite is `--unclaim`ed with the gap named.
- **Lifecycle**: `pending → (claim) → in_progress → (report) → review →
  (verify) → completed`; `unclaim` and `verify --reject` return to `pending` /
  `in_progress`. Workers claim slices for themselves; orchestrators (or a
  designated verifier) verify review slices.
- **Comment / update**: `task-db.py update <id> --status <s> --reason "<why>"`.
  A same-status update records nothing; notes that are not status changes go to
  a governance issue event, not `update --reason`.
- **Close**: `task-db.py update <id> --status completed` (archived at session
  end via `save-end`).

## Wayfinding operations

Used by `/wayfinder`. Because the task-db has no native issue-dependency graph
exposed to the CLI, represent the **map** as a `story` row and each **decision
ticket** as a `slice` under it, with `blocked`/`waiting` tags for externally
gated items. The **frontier** = the story's slices in `pending` with an empty
prerequisite chain. **Resolve** a ticket: answer in a `update --reason` note then
transition the slice (`completed`), and append the outcome to the story row's
content.

## When a skill says "publish to the issue tracker"

Create a task-db row (`task-db.py add`) with the repo tagged
`steadfaste-fleet`.

## When a skill says "fetch the relevant ticket"

`task-db.py list --status pending --repo steadfaste-fleet`, or `list <id>` /
`pending` for a specific slice.
